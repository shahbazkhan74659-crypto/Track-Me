# Architecture

This describes the **actual current implementation**. Two things coexist in the repo: the approved interactive design prototype (unchanged, not deployable — kept as the visual/interaction reference), and the production Next.js/TypeScript app. As of Phase 15 (2026-09-05), the app is functionally whole end to end and mobile-responsive: `app/page.tsx` gates access with a real login check, and once authenticated, `components/AttendanceApp.tsx` coordinates real data for the profile/Salary-Setup header (Phase 12), the stat cards (Phase 11), and the clickable calendar (Phase 10's grid + Phase 13's date-entry modal) against the real backend (Phases 3–8) — no more local-only placeholder state anywhere in the frontend, and the whole layout adapts down to phone-width screens (Phase 15). As of Phase 16 (complete, 2026-09-05), the app also has a real automated test suite (Playwright E2E + component tests — see "Testing (Phase 16)" below) covering auth, salary, calendar entries, the stats formula, and the mobile layout, plus production-readiness work — security (rate limiting, headers), an env var audit, styled error pages, Node version pinning, and crawler exclusion (see "Production Readiness (Phase 16)" below) — verified under a real `next build && next start`, not just `next dev`. What's left is deployment itself: the Neon/Render/UptimeRobot phases (17–19) before a final live-site check (Phase 20). See `DECISIONS.md` for the reasoning behind building it this way, and `PROJECT.md`/`PHASES.md` for what comes next. The **Planned Production Architecture** section below is now almost entirely realized — see `CLAUDE.md` rule 9: do not treat anything still marked planned there as implemented until it actually is.

## Login Backend (Phase 3 scaffold)

- **Database access**: `lib/db.ts` exports a singleton `pg.Pool` (cached on `global` in dev to survive hot reload) reading `DATABASE_URL` from `.env.local` (gitignored; `.env.example` documents the shape). The connection uses a dedicated, least-privilege Postgres role `trackme_app` — not the `postgres` superuser — created during Phase 3, scoped to `CONNECT` on `trackme_dev` and CRUD on just the `users`/`sessions` tables. See `DECISIONS.md`.
- **Schema** (`db/schema.sql`, applied by hand via `psql`, no ORM/migration tool): `users (id, username unique, password_hash, created_at)` and `sessions (id text primary key — the opaque session token itself, user_id fk, created_at, expires_at)`.
- **Auth logic** (`lib/auth.ts`): `createSession`/`getSessionUser`/`deleteSession`, a 32-byte random hex token as the session id, 30-day expiry, cookie name `trackme_session` (httpOnly, `sameSite: lax`, `secure` in production).
- **API routes**: `app/api/auth/login/route.ts` (POST — bcrypt-verifies against `users`, generic "invalid username or password" error regardless of which part was wrong, sets the session cookie on success), `app/api/auth/logout/route.ts` (POST — deletes the session row, clears the cookie), `app/api/auth/session/route.ts` (GET — reports `{ authenticated, username? }` from the current cookie).
- **No signup route exists.** The single account is created/reset via `scripts/seed-user.mjs` (`node scripts/seed-user.mjs <username> <password>`), run manually by the owner — not part of the running app. See `DECISIONS.md`'s "Phase 3 narrowed to login-only" entry.
- **Test harness (historical)**: `app/page.tsx` (the Phase 2 temporary page) included a plain login form exercising all three auth routes and showing live session status, until the page was removed in Phase 8; see "Full Backend Testing & Temporary Page Removal (Phase 8)" below for how these routes are now verified.
- **Not yet built**: no shared middleware guarding routes — each protected route calls `requireAuth` itself (see below) rather than a central middleware layer; no rate limiting on login attempts; no password reset. A frontend login page now exists (Phase 14, below) using this same backend directly — see "Login & Data Wiring (Phase 14)".

## Calendar Backend (Phase 5)

- **`lib/calendar.ts`**: pure, dependency-free calendar utility module, reused by every future phase that touches dates (Phase 6 entries, Phase 7 calculations). Exports `getTodayIST()` (current Asia/Kolkata date via `Intl.DateTimeFormat`, timezone-independent of the server process — see `DECISIONS.md` for why this matters), `normalizeYearMonth(year, month)` (rolls any integer month into 0-11 range with year carry, e.g. for Dec/Jan navigation rollover), `daysInMonth`, `weekdayOfFirst`, `weekdayOf` (all UTC-anchored Gregorian arithmetic, leap-year correct), and `buildMonthGrid(year, month, today?)` (the fixed 6x7/42-cell, Sunday-first grid, including real year/month/day for leading/trailing adjacent-month cells — reproduces the approved prototype's `computeCells` algorithm exactly, but timezone-safely).
- **API route** (`app/api/calendar/route.ts`): `GET` only, `requireAuth`-gated (401 if not logged in). Optional `year`/`month` query params (0-indexed month, matching the entries-key convention); omitting both defaults to the current Asia/Kolkata month. Returns 400 if only one of `year`/`month` is given, either is non-integer, or `year` is outside `[1900, 2200]`. Response shape: `{ today: {year, month, day, weekday}, requested: {year, month}, cells: CalendarCell[] }` (42 entries).
- **Test harness (historical)**: `app/page.tsx`'s Calendar section (visible only when authenticated) showed the live Asia/Kolkata "today" reading, a year/month input form, and a plain 7-column grid rendering of the 42 returned cells (dimmed for adjacent-month days, bordered for today) — until the page was removed in Phase 8; see "Full Backend Testing & Temporary Page Removal (Phase 8)" below.
- **Not yet built**: no persistence — this phase is a pure computation service. The `entries`/attendance table (status, advance amount, keyed by date) is Phase 6, not this phase.

## Clickable Date Modal Backend (Phase 6)

- **Schema**: a new `entries` table (`db/schema.sql`) — `user_id` FK (cascade delete), `year`/`month` (0-indexed, matching `lib/calendar.ts`)/`day`, `status TEXT CHECK (IN 'present','half','leave')`, `advance_on BOOLEAN`, `advance NUMERIC(10,2) CHECK (>= 0)`, `created_at`/`updated_at`, and `UNIQUE (user_id, year, month, day)` — the upsert target and the "at most one entry per date" invariant; no row for a date means no entry (mirrors the prototype's outright delete-on-clear). Created and granted to `trackme_app` by the owner via `psql` (`CREATE TABLE` and `GRANT` both require the `postgres` superuser, same as every prior schema change).
- **API route** (`app/api/entries/route.ts`): one route, `requireAuth`-gated. `GET ?year=&month=` mirrors `/api/calendar`'s validation/defaulting and rolls the month over via `normalizeYearMonth` (it's a "view a month" operation); returns `{ year, month, entries: [{day, status, advanceOn, advance}] }`, sparse — only days with a persisted row. `PUT` body `{year, month, day, status, advanceOn, advance}` upserts via `INSERT ... ON CONFLICT (user_id, year, month, day) DO UPDATE`; unlike `GET`, it does **not** roll over an out-of-range month/day (400 instead) since it targets one exact row a specific calendar cell was clicked on, not a navigable view. `DELETE` body `{year, month, day}` clears one entry, idempotently. Validation reproduces the prototype's invariants: `status` required and must be exactly one of the three values (server-side twin of the Done button's disabled-without-status rule); `advanceOn` must be boolean; when false, `advance` is force-set to `0` server-side regardless of the request body; when true, `advance` must be a finite number `>= 0` — zero is explicitly allowed and persists `advanceOn: true` (the ₹0-advance-must-still-count-as-taken invariant). Day-range validation uses `lib/calendar.ts`'s `daysInMonth` (leap-year correct), not a hardcoded 1–31. Every query is scoped to `requireAuth`'s `user.id`, never a body-supplied id.
- **Test harness (historical)**: `app/page.tsx`'s Date Entry section reused the Calendar section's grid as the click target — clicking a current-month day opened an inline editor prefilled from any existing entry (status radios, an advance checkbox revealing an amount field, Save disabled until a status is chosen, Clear shown only when the day already had a saved entry) — until the page was removed in Phase 8; see "Full Backend Testing & Temporary Page Removal (Phase 8)" below.
- **Not yet built (at the time this phase landed)**: no aggregate calculations (Earned So Far / Advance Taken / Net Payable) — this phase's `GET` deliberately returned only raw per-day rows. Aggregation is now built — see the "Salary / Advance / Attendance Calculation Backend (Phase 7)" section below.

## Salary / Advance / Attendance Calculation Backend (Phase 7)

- **Schema**: none — pure computation over the existing `users.per_day_salary` and `entries` tables from Phases 4 and 6.
- **API route** (`app/api/summary/route.ts`): `GET` only, `requireAuth`-gated, same `year`/`month` query-param contract as `/api/calendar` and `/api/entries GET` (both-or-neither, integers, year `[1900,2200]`, defaults to the current Asia/Kolkata month via `getTodayIST()`, rolls an out-of-range month over via `normalizeYearMonth` — a "view a month's summary" operation, same category as those two, not a single-row-identity operation like `entries`' `PUT`/`DELETE`). Runs two queries via `Promise.all` (no join, matching this codebase's existing flat-query style): `SELECT per_day_salary FROM users WHERE id = $1`, and one aggregation over `entries` using Postgres `FILTER` clauses:
  ```sql
  SELECT
    COUNT(*) FILTER (WHERE status = 'present') AS present_days,
    COUNT(*) FILTER (WHERE status = 'half') AS half_days,
    COUNT(*) FILTER (WHERE status = 'leave') AS leave_days,
    COALESCE(SUM(advance) FILTER (WHERE advance_on), 0) AS advance_taken
  FROM entries WHERE user_id = $1 AND year = $2 AND month = $3
  ```
  Formula (matches the approved prototype's `renderVals()` exactly): `earned = presentDays × perDaySalary + halfDays × (perDaySalary ÷ 2)`, `netPayable = earned − advanceTaken`. `leaveDays` is computed and returned but never feeds the money math, matching the prototype. When `per_day_salary` is `NULL` (a valid, unset-rate account state — see `DECISIONS.md`'s Phase 4 note), `earned`/`netPayable` are `null` in the response but the endpoint still returns 200; `presentDays`/`halfDays`/`leaveDays`/`advanceTaken` are always real numbers regardless. Response: `{ year, month, perDaySalary, presentDays, halfDays, leaveDays, advanceTaken, earned, netPayable }` — raw numbers throughout, no currency formatting (that's a frontend concern for Phases 9+).
- **Test harness (historical)**: `app/page.tsx`'s Summary section showed three plain cards (Earned So Far / Advance Taken / Net Payable) with present/half/leave subtext, refreshed on month navigation and — since the owner wanted live recalculation "on every date entry" — also re-fetched immediately after `handleSaveEntry`, `handleClearEntry`, and `handleSaveSalary` succeeded, so the cards updated without a page reload — until the page was removed in Phase 8; see "Full Backend Testing & Temporary Page Removal (Phase 8)" below.
- **Not yet built (at the time this phase landed)**: no frontend beyond the test harness (Phases 9–13); no currency/locale formatting (deferred to those phases, per the prototype's `fmtINR` helper being a display concern, not backend logic).

## Full Backend Testing & Temporary Page Removal (Phase 8)

- **Test script** (`scripts/test-backend.mjs`): plain Node ESM script (no new dependencies, same convention as `scripts/seed-user.mjs`), run via `node scripts/test-backend.mjs <username> <password>` against the running dev server. Exercises every route from Phases 3–7 over real HTTP using `fetch`, manually capturing and re-attaching the `trackme_session` cookie (Node's `fetch` has no browser-style cookie jar). All entry-table assertions run inside a dedicated fake test year (2099, split across three months so CRUD/validation tests, the hand-calculated summary check, and the adjacent-month leak check don't interfere with each other) — never a real attendance month — and are deleted again (plus a pre-flight wipe of any stray rows from a previous interrupted run), so the script is safe to run repeatedly. `users.per_day_salary` — the one non-month-scoped mutable value in this app — is captured before any test `PUT` and restored to its exact original value in a `finally` block, including a direct Postgres `UPDATE ... SET per_day_salary = NULL` fallback for the one case `PUT /api/salary` cannot express itself. Reports a pass/fail line per assertion and a final summary, exiting non-zero if anything failed. Ran twice against the live dev server and real database: 73/73 assertions passed both times, and a `psql` snapshot before/after confirmed the real account's `per_day_salary` and current-month entries were byte-for-byte unchanged.

No `"use client"`, no hooks, no `fetch`, no imports from `lib/db.ts`/`lib/auth.ts`/`lib/calendar.ts` at the page level — confirmed via grep. Plain inline React styles are used throughout, matching every other page/route already in this codebase; no CSS framework or CSS-in-JS library was introduced.

### Scrolling fix (post-Phase 11, 2026-09-05)
Phase 9 originally pinned the page to exactly one viewport (`height:100vh`/`overflow:hidden` on the page div, `height:100%`/`overflow:hidden` on `html`/`body`) to fix a white-background-sliver bug at a time when the page had no content. Once Phase 10 (calendar) and Phase 11 (stat cards) added real content, that fixed-viewport rule made the page **uncrollable** — content taller than the viewport was simply clipped, a real bug the owner caught visually. Fixed by switching to `min-height` everywhere (page div: `min-height:100vh`; `html`/`body`: `min-height:100%`) and dropping `overflow:hidden` in favor of `overflow-x:hidden` on `html`/`body` only (still prevents horizontal scroll/white edges, no longer blocks vertical scroll). The original white-sliver bug doesn't return because the fix that solved it — `<body>` carrying the dark background directly, not just the inner div — was independent of the fixed-height/overflow-hidden rule and is unchanged. See `DECISIONS.md`'s "Frontend shell reverted to natural page scroll" entry.
- **Next.js dev indicator disabled**: `next.config.ts` sets `devIndicators: false` — the on-screen "N" badge/route-info popup Next.js shows in development is unnecessary noise now that backend testing (Phase 8) is done and isn't part of the app itself.
- **Not yet built at the time**: header/profile/Salary-Setup UI, calendar UI, stat cards, and any backend connection — all now built (Phases 10–14, see below).

## Production Readiness (Phase 16)

- **Security posture, discussed and scoped deliberately**: this is a small, single/two-user personal tool, not a multi-tenant product handling payment data — reviewed with the owner what that actually implies. The existing fundamentals were already proportionate and needed no change: parameterized SQL throughout (`pg`'s `$1`/`$2` placeholders, no string-built queries anywhere), bcrypt-hashed passwords, DB-backed sessions with `httpOnly`/`sameSite:"lax"`/`secure`-in-production cookies, no public signup route, and React's default JSX escaping (no `dangerouslySetInnerHTML` anywhere in the app). A CSP, WAF, or compliance tooling (SOC2-style controls, pen testing) were explicitly considered and rejected as disproportionate to this app's actual risk — CSP in particular would need real work given the inline-`style`-everywhere approach `DECISIONS.md`'s Phase 9 entry locked in, for a threat (user-generated/third-party script injection) this app doesn't have a surface for.
- **`lib/rateLimit.ts`** (new): an in-memory, per-IP login-attempt limiter — `checkRateLimit`/`recordFailedAttempt`/`resetRateLimit`, a `Map` keyed by the requester's IP, 5 failed attempts per rolling 15-minute window, reset immediately on a successful login. Wired into `app/api/auth/login/route.ts`: checked before any DB query runs, and a blocked request gets `429` with a `Retry-After` header rather than reaching the bcrypt comparison at all. In-memory (not DB-backed) is a deliberate choice — Render serves this app as one long-running Node process (not per-request serverless functions), so the state persists across requests within a deploy and simply resets on restart/redeploy, an acceptable tradeoff at this scale. IP is read from `x-forwarded-for` (the header a real reverse proxy — Render's, in production — sets), falling back to the literal string `"unknown"` when absent, which is what every request hits in local `next dev` (no proxy in front of it) — meaning all local requests share one bucket. Worth knowing if testing rate-limiting locally: it's easy to lock out your own next real login attempt for the rest of the 15-minute window, as happened once during this session's own verification (fixed by restarting the dev server, which clears the in-memory map).
- **`next.config.ts`**: gained an `async headers()` export applying five response headers to every route (`/:path*`): `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()` (this app uses none of those browser features), and `Strict-Transport-Security: max-age=63072000; includeSubDomains` (inert over plain HTTP in local dev; takes effect once deployed over HTTPS on Render). No `preload` directive on HSTS — that requires submitting the domain to browsers' preload lists, a one-way decision not appropriate to make without the owner's explicit ask.

## Application Structure (prototype only)

Single artboard, single component (`Main.dc.html`), no routing. All state lives client-side, in memory, in the component's React-like `state`:

- `year` / `month` — the calendar's currently displayed month (0-indexed month).
- `perDaySalary` — the single per-day rate the owner sets via Salary Setup; every other figure is derived from it.
- `entries` — a plain object keyed `"<year>-<month>-<day>"` (no zero-padding) → `{ status: 'present' | 'half' | 'leave', advanceOn: boolean, advance: number }`.
- `openDate` + `draftStatus` / `draftAdvanceOn` / `draftAdvanceAmt` — the currently-open date-entry modal's target date and in-progress (unsaved) edits.
- `salaryOpen` / `salaryDraft` — the Salary Setup modal's open state and in-progress input.

The calendar grid (42 cells, 6 fixed rows) and all derived display values (formatted ₹ labels, per-status button/cell styling, the "today" ring, stat-card totals) are recomputed from `state` on every render inside `renderVals()` — nothing is cached or memoized beyond React's own re-render.

## Data / Persistence

None. All state is in-memory only and is lost on page reload — an explicit, current limitation of the prototype, not yet addressed. The production persistence approach (local storage, a backend + database, or something else) has not been decided — see `DECISIONS.md`.

## Important Invariants

Documented so a future production build doesn't regress behavior already established (and debugged) in the prototype:

- Entry keys are built as `` `${year}-${month}-${day}` `` with a **0-indexed month** and **no zero-padding** on month or day — this exact format is relied on both when writing entries and when filtering them by the currently displayed month (a string-prefix match on `` `${year}-${month}-` ``).
- Advance tracking uses a dedicated `advanceOn` boolean, separate from `advance` (the amount). Do not go back to treating `advance > 0` as "was an advance taken" — a real ₹0 advance must still count as taken; this was a bug found and fixed during prototyping (see `TASKS.md`).
- The Done button in the date-entry modal is disabled until a status (Present/Half-Day/Leave) is selected; an advance amount alone, with no status, cannot be saved.
- Earned So Far = (present days × per-day rate) + (half days × per-day rate ÷ 2), summed over entries in the currently displayed month only.
- Net Payable = Earned So Far − Advance Taken, both computed over the currently displayed month only (not the whole year, not "up to today" if viewing a different month).
- Calendar navigation (prev/next month) rolls the year over automatically at the Dec/Jan boundary; there is a separate "Today" shortcut back to the current month.

## Planned Production Architecture

**Mostly realized as of Phase 15** — framework, frontend, backend, auth, and mobile responsiveness below are all now actually built (see the phase sections above); only testing/deployment (production readiness, database host, hosting, uptime monitoring) remains planned. See `DECISIONS.md`'s "Production stack locked" entry and `PHASES.md`.

- **Framework:** Next.js, written in TypeScript, for both the frontend and the backend — one project, one language. No separate Express/API server. **Built.**
- **Frontend:** Plain React (via Next.js), not a server-rendered-template-plus-islands layer. Interactive actions (saving a date entry, changing salary, live stat recalculation) call Next.js API routes via `fetch` (AJAX-style, no full page reloads) — **built in Phase 14** (`components/AttendanceApp.tsx`), carrying forward the interaction feel established by the prototype.
- **Backend:** Next.js API routes / route handlers, same project as the frontend. **Built** (Phases 3–8).
- **Database:** PostgreSQL — a local Postgres install for day-to-day development (**built**, Phase 1), Neon (serverless Postgres) in production (**built**, Phase 17). Real persisted rows replace the prototype's in-memory `entries` object; the prototype's entry shape and invariants were the schema's starting point, not a redesign.
- **Hosting:** Render, free tier. **Not yet done** — Phase 18.
- **Uptime:** An UptimeRobot monitor pinging the deployed app, to counter Render free tier's idle spin-down. **Not yet done** — Phase 19.
- **Auth:** A real login backend (Phase 3) plus a real frontend login gate (Phase 14). **Built.** The app remains single-user in scope (not multi-tenant); see `DECISIONS.md`'s "Login/signup backend added to the roadmap" entry.
